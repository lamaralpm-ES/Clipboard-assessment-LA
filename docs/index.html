Matching Approach · What I Actually Did

The matching logic used the strongest evidence first and avoided changing CRM records when the evidence was weak.

Step 1 · Standardize the source data

I scraped all current Bellhaven community pages and standardized names and addresses so formatting differences such as “West” vs “W”, street abbreviations, capitalization and punctuation would not create false mismatches.

Step 2 · Look for the same physical facility

I first compared normalized street, city, state and ZIP. Matching the physical facility was treated as stronger evidence than the account name because names can change after an ownership transition.

Step 3 · Use name + geography when the address differed

If there was no exact address match, I looked for the same normalized facility name within the same city/state. This helped with PO Boxes and outdated address formatting without matching unrelated accounts elsewhere.

Step 4 · Use controlled fuzzy matching only within the same area

For remaining cases, I compared similar facility names only among accounts in the same city/state and required a strong enough match before proposing a change.

Step 5 · Apply CRM business rules after the match

Once a likely record was identified, I checked parent ownership, status, revenue, outstanding AR and duplicates to decide whether the correct action was update, direct re-parent, CHOW, create, duplicate handling or Needs Review.

Step 6 · Human review before any write

The system did not automatically change the CRM. I reviewed each proposal and its evidence in the app, then explicitly approved or rejected it. Only approved items were written through the API.

Iteration & Learnings

The first pass was tested against the live data, and the results showed where the matching approach needed improvement. I refined the logic before applying changes.

1
Initial matching was too narrow

The first dry run surfaced only a small subset of expected discrepancies. I revisited the matcher, improved address normalization, and changed the sequence so it first looked for the same physical location, then name matches within the same city/state, and only then used controlled fuzzy matching.

2
Ownership history created ambiguous cases

Facilities such as Kettering and Union Square showed why same-city or similar-name matches are not enough. When the physical-location evidence was not strong enough, I did not change the existing CRM account or force a re-parent.

3
Billing history changed the correct CRM action

The CHOW rule meant that some apparent re-parenting tasks actually required preserving the historical account and creating a successor. That business rule was built directly into proposal generation.

4
Final-state validation mattered

After I reviewed all proposals and approved the changes, I reran the pipeline as a final check. It returned 0 open proposals, confirming that the approved changes had been applied and there was nothing left for review.

Safety & Controls

No automatic CRM writes

Scraping and matching are read-only. A CRM change only happens after a reviewer explicitly approves the proposal.

Previously reviewed items are remembered

The app stores decisions that were already made so the same proposal does not keep coming back for review on the next run.

Credentials kept out of the code

The assessment API token is never stored in source control or committed to GitHub.

How AI Was Used

I used ChatGPT as a development and analysis partner to inspect API behavior, develop and debug the matching pipeline and review app, and pressure-test edge cases. AI accelerated implementation and testing, while I reviewed the underlying CRM evidence and business rules before approving any write.
